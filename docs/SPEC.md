# OurHours 仕様メモ（設計・意思決定ログ）

> **目的**：本ドキュメントは `OurHours` の仕様だけでなく、「**なぜこの仕様にしたのか（Why）**」「**検討して見送った案**」「**外部レビューの指摘と反映内容**」「**実装前に実機実験で確認すべき未確定事項**」をまとめて記録するものです。開発中に「ここなんでこうしたんだっけ？」となったときに立ち返るためのベース資料として使います。

## 1. プロダクト概要

| 項目 | 内容 |
|---|---|
| **アプリ名** | **OurHours**（アワー・アワーズ） |
| **ネーミングの由来** | 英語の `Our`（私たちの）と `Hour`（時間）が同じ発音で韻を踏んでいること＋「ふたりで積み重ねてきた時間たち」の意味。日本語読みだと「泡泡〜s（あわあわ〜ず）」になって可愛い。 |
| **ビジュアル方向性** | **泡っぽいデザイン**（シャボン玉・ぷかぷか積み上がる時間など、やさしく軽やかなトーン） |
| **コンセプト** | 地図や現在地を監視し合うのではなく、**Bluetooth（即時検知）と暗号化した正確な位置情報（2端末間 CloudKit 突き合わせ補完）の和集合**を使って「**実際に一緒にいた日と時間**」だけを自動で取りこぼしなく記録し、ふたりの思い出につなげるカップル向けアプリ。 |
| **対象OS・プラットフォーム** | **iOS専用（iOS 26 以上）**／iPhone同士 |
| **公開方針** | App Storeで一般公開予定（まずは自分・彼女・友達にも使ってもらう） |
| **バックエンド構成** | サーバーレス（**CloudKit** 単体で構成） |

### なぜ「iOS 26 以上」に絞るのか
- 古いOS向けの互換分岐やワークアラウンドを切れる。
- iOS 17以降のCoreBluetooth自動再接続、iOS 18以降のCloudKit 1回限り招待URL、`CKSyncEngine` などの最新APIを最初から前提にでき、設計と実装がシンプルになる。

### なぜ「地図UIを出さずに位置情報×BLEを併用する」のか
- 実機一晩テストの結果、iOS バックグラウンド BLE だけではスリープや画面消灯・プロセス終了時に検出漏れ（同じ場所にいるのに記録されない時間）が発生し得ることが判明したため。
- 一方で「居場所をリアルタイム地図で監視する」UIは一切作らず、**正確な位置情報（`CLVisit` / 100m出口ジオフェンス / 大幅位置変化）をペア専用共有鍵で E2EE 暗号化して CloudKit で突き合わせ、同じ時間帯・近接圏内だった事実から滞在時間だけを算出する**ことで、「監視感ゼロ」と「取りこぼし根絶」を両立する。
- 生の座標データは 14 日で自動削除し、確定した結合滞在区間（開始・終了時刻と平均距離のみ）を長期保持する。

## 2. iOSバックグラウンドBluetoothの制約と、見送ったアプローチ

仕様を決める前提として、iPhone同士（iOS ↔ iOS）のバックグラウンドBluetooth（CoreBluetooth）には以下の制約がある。

### 前提となるiOSの制約
1. **画面消灯（ロック状態）時の新規探索制限（Overflow Area問題）**
   - iPhoneがバックグラウンドで電波を出すと、省電力のためローカル名は消え、Service UUIDはApple独自の領域（Overflow Area）に入る。
   - 電波を出す側（Peripheral）は画面オフでも出続けるが、探す側（Central）は**画面が消灯しているとOverflow Areaの探索が極端に落ちる／止まりやすい**。
   - 画面が点いた瞬間（ロック解除せずとも、通知で光る・時計を見る・持ち上げる等）に探索が動きやすい。
2. **Overflow Areaのハッシュ衝突（誤検知リスク）**
   - Overflow AreaはUUIDそのものではなく128bitビットマスクで照合されるため、満員電車などで他人の別BLEアプリと約1/128の確率で衝突し、発見イベントが発火し得る。
3. **アプリの手動完全終了（スワイプ終了）と再起動**
   - OS都合のメモリ解放終了であれば、状態復元（State Preservation & Restoration）によりBluetoothイベントで自動復帰できる可能性がある。
   - 一方、ユーザーが**マルチタスク画面から上にスワイプして完全終了した場合や、iPhone再起動後（初回ロック解除前など）**は、次にアプリを開くまでバックグラウンドBluetoothは動かない。
4. **確立済み接続の維持と切断検知**
   - 新規探索は画面消灯に弱いが、一度確立したBLE接続は画面オフのまま寝ても維持されやすく、離れたときの切断イベントでOSがアプリを起こしてくれる場合がある（ただし朝までの維持や全イベント捕捉はOS保証外のため実測が必要）。

### 検討したが見送ったアプローチ（Why）
| 検討案 | 採用しなかった理由 |
|---|---|
| **Live Activityで夜間のバックグラウンド探索を維持する** | iOS 26以降でも、画面がロックして完全消灯すると探索制限が戻るため夜間の解決策にならない。またローカルのバックグラウンド起動からは直接開始できず、8時間上限もある。<br>※将来的に「デート中 💕 3時間」のような**UI演出**として使う余地はある。 |
| **市販の小型iBeaconキーホルダーをお揃いで持つ** | iBeacon領域監視はスワイプ終了・再起動後でもOSが強制起動してくれる強みがあるが、「iPhone同士だけで完結したい」コンセプトと外れ、位置情報の「常に許可」も必要になるため不採用。 |

## 3. コア仕様：Bluetoothによる自動記録

### 3.1 基本フロー（ユーザー体験）
1. **初回セットアップ（会っているときに1回だけ）**
   - 2人が対面している状態で、片方がQRコードを表示し、もう片方がスキャンしてペアリング＆CloudKit共有を完了する。
2. **普段の動き（以降は自動）**
   - 2人が近づく → 裏で自動検知＆相互認証 → **接続を維持（開始時刻を記録）**
   - 一緒にいる間（2人で寝て画面を触らない時間も含む）→ 接続をキープ
   - バイバイして離れる → 切断を検知（**終了時刻を記録**）
3. **記録の表示**
   - 最初から「**◯月◯日 ◯時〜◯時（何時間）**」という開始〜終了の区間を記録する。
   - その区間データから「一緒にいた日のカレンダー」と「累計／月別の滞在時間」の両方を表示する。

### 3.2 なぜこの仕組みにしたか（設計判断）
* **両端末とも「探す側（Central）」＋「出す側（Peripheral）」を両方持つ**
  - 片方が画面オフ・スワイプ終了になっていても、もう片方が動いていれば記録を救えるようにするため。
  - 接続後は不要な探索を止め、毎分通信するような電池を食う生存確認はしない（平日の別行動時の電池消費も抑える）。
* **最小単位を「1時間」にする**
  - 分単位の厳密な計測は行わない。
  - 理由：会ってから繋がるまでの数分のタイムラグ、トイレや別室移動による短時間切断、寝ている間の微細なズレを、仕様として気にならないレベルに吸収するため。
* **発見だけで記録せず、必ずペア専用の相互認証を通す**
  - 理由：Overflow Areaのビット衝突による「無関係な他人のiPhone」の誤検知を防ぐため。
  - Bluetoothの端末識別子（アドレス等はローテーションされる）を、機種変更まで通用する本人確認には使わない。
* **対面設定済みの「自動再接続」を優先検証する**
  - 外部レビューの指摘を受け、未接続からの探索だけでなく、iOS 17以降の自動再接続（`CBConnectPeripheralOptionEnableAutoReconnect`）を使った再接続成功率もプロトタイプで比較検証する。

## 4. 集計・補正・エッジケースの仕様（外部レビュー反映）

外部レビューの指摘「Bluetoothが観測するのはあくまで『端末同士の接近』であり、通信が完璧でも現実とズレることがある（スマホを家に置いて片方だけ外出、30分のランチ、検知漏れ等）」を踏まえ、以下を仕様として採用する。

### 4.1 「自動記録（候補）＋ 手動修正」を前提にする
- 自動記録を絶対視せず、**本人が記録を追加・訂正・削除できる導線**を必ず用意する。
- **手動で訂正した記録は、あとから遅れて届いた自動記録で上書きしない**ルールにする。

### 4.2 2端末分のログ統合ルール（BLE ∪ 位置情報・二重計上防止）
- 各端末は自分が観測した BLE 記録と暗号化済み位置滞在バケットを同期し（2人で同じ生レコードを上書き競合させない）、端末内で突き合わせて `LocationMatchedSession` を算出する。
- 表示・集計時は **BLE 自動記録 ∪ 位置補完記録 ∪ 手動記録** の区間を統合（Interval Union）し、**重なりは一度だけ数える**。BLE で 95% 以上カバーされている区間は詳細リストの重複表示も抑制する。
- トイレや電波の揺らぎによる短い切断をつなげるのは、**その前後で同じ相手を再認証できた場合に限る**（位置補完側は最大 10 分までの短ギャップを結合、3 分未満のノイズは除外）。

### 4.3 「終了不明」の扱い
* **どんなときに起きるか**
  - 接続中（開始時刻だけ記録された状態）に、電池切れ・手動スワイプ終了・iPhone再起動・クラッシュ等で切断イベントを受け取れなかったとき。
* **なぜ対策が必要か**
  - 翌朝アプリを開いた時刻を終了にしてしまうと、数時間のデートが「20時間一緒だった」等と過大計上されてしまうため。
* **ルール**
  - もう片方のiPhoneに正常な終了時刻があれば、そちらを採用して補完する。
  - 両方とも終了時刻が抜けていた場合は「**終了不明**」として扱い、勝手に時間加算せずユーザーに手動補完を促す。

### 4.4 日・月境界とタイムゾーン
- 2人のカレンダーで基準とするタイムゾーンを決め、日・月をまたぐ区間を分割する。
- 例：月末 `23:40〜翌月 00:20`（40分）を、両月に各1時間（計2時間）と二重計上しないようにする。

### 4.5 プライバシー上「共有・表示しない」情報
監視アプリにしないため、以下はUIに表示・一般公開しない。
- **相手の現在地・移動経路の地図表示**：位置情報は `BLE` の取りこぼしを補う突き合わせ用途に限定し、地図画面や生座標 UI は実装しない。送信データも `PairConfiguration` の共有秘密鍵（HKDF-SHA256 + AES-GCM）で端末内暗号化し、生の位置バケットは 14 日で自動削除、ペア解除時に自分側の CloudKit レコードも消去する。
- 相手のアプリ最終起動時刻
- Bluetoothをオフにした理由・状態の詳細
- リアルタイムの接離ステータス（生ログは短期保持に留める）

## 5. CloudKit共有・セットアップ・機種変更・解除

### 5.1 QRセットアップとCloudKit共有
- 別々の有効なiCloudアカウントを前提とする。
- iOS 18以降の **1回限りの招待URL（`oneTimeURLParticipant`）** を使い、相手の電話番号やメールアドレスを事前入力せずにQRコードで招待する。
- 招待受諾前のURLは第三者が入手すると使えるリスクがあるため、**最初は空の共有ゾーンから開始し、両端末の対面確認（CloudKit参加受諾＋Bluetooth相互認証）が完了してから履歴同期を始める**。
- 圏外や権限拒否などで中断しても「設定途中」から再開できる設計にする。

### 5.2 オフライン・同期エラーの扱い
- 観測ログはまずローカル保存し、同じ観測を再送しても二重計上しない（冪等にする）。
- CloudKitのプッシュ変更通知は「同期のきっかけ」として扱い、即時到着や全件配信を前提にしない。アプリ起動・復帰時にも差分同期を行う。
- 圏外・iCloud未ログイン・所有者のiCloud容量不足はエラーで握りつぶさず「同期待ち」と分かる表示にする。

### 5.3 「別れたとき」と「機種変更」の仕様統合
* **背景（Why）**
  - カップルアプリに「別れたときの全削除ボタン」を置くのは縁起が悪く避けたい。
  - 一方、単にアプリを削除しただけではCloudKitの共有関係が切れず、App Store審査でも「ユーザー自身が自動記録・共有を止められる操作」が求められる。
* **方針**
  - 縁起の悪い表現は使わず、ホームまたは設定の分かりやすい場所に **「自動記録のON/OFF」**、設定画面の奥に **「ペア連携を解除（機種変更・再設定）」** を配置し、**機種変更・審査対策・関係終了の3つを1つの導線で兼ねる**。
  - 連携解除を実行したら、その端末の認証・計測・未送信データの送信を即座に止める（オフライン時は「この端末で停止済み／クラウド反映待ち」を区別）。
  - 解除画面では「今後の共有停止」「過去の履歴の扱い」「相手側に残るもの」の違いを明記する。
* **機種変更時の考慮**
  - 同じiCloudから過去履歴を復元する操作と、Bluetoothの計測担当端末を入れ替える操作を分ける。
  - 新しいiPhoneで対面QR再設定を行った際は、**旧端末の認証を失効**させる（自宅に置いた旧iPhoneが誤カウントし続けるのを防ぐ）。
  - 未送信データは当時のアカウント＆ペアIDに紐づけ、別アカウントや再ペアリング先に混入させない。

## 6. 機能構成（MVP と 将来拡張）

### 日常的にアプリを開く理由づくり（タスクキル対策 × 三日坊主防止）
壁打ちで出たアイデア：
- デート予定の登録
- 2人で書き込める共有メモ帳
- 一緒に行った場所の記録
- これから行きたい場所・やりたいことリスト

**Why**：iOSの仕様上、手動でスワイプ終了されると次にアプリを開くまでBluetooth自動記録が止まる。普段から自然に開く機能があればアプリが生存し続けやすく、逆に「自動記録された日と時間」が思い出を書くきっかけになり、カップルアプリ特有の三日坊主を防げる。

### フェーズ分け（外部レビュー反映）
ただし、**肝心のBluetooth自動記録の精度を確かめる前に付帯機能を作り込むのはリスクが高い**ため、段階的に作る。

* **フェーズ0：BLE実機検証プロトタイプ（最優先）**
  - UIなし・CloudKitなし。Bluetoothの接続・再接続・一晩維持・切断ログ計測のみ。
* **フェーズ1：MVP（最小リリース構成）**
  - 対面QRペアリング
  - 自動記録された「開始〜終了の区間」と「カレンダー表示」
  - 記録の手動追加・訂正・削除
  - その日の記録に添える「一言メモ」
  - 自動記録ON/OFF、ペア連携解除（機種変更・再設定）
* **フェーズ2：日常利用・拡張機能（コア体験が成立してから追加）**
  - デート予定、共有メモ帳、行った場所／行きたい場所リスト
  - Live Activityによるデート中演出（任意）

> 未実装の将来機能アイデア、確定したUI刷新方針、および実機検証の技術知見バックログは [IDEAS.md](IDEAS.md) に別途まとめています。

## 7. App Store審査の事前対策（一般公開向け）

`bluetooth-central`・`bluetooth-peripheral`・`location` の Background Modes を使うため、以下を最初から設計に組み込む。

1. **審査メモの明文化**
   - 画面を閉じている間に「BLE探索/広告」および「省電力な滞在・移動イベント（`CLVisit` / 100mジオフェンス / SLC）」それぞれがなぜユーザー機能（取りこぼしのない滞在時間自動記録）に必要なのか、地図表示を行わない E2EE 設計であること、およびユーザーが設定画面からどう停止できるかを明記する（ガイドライン 2.5.4）。
   - State Preservation & Restoration を実装する。
2. **権限とプライバシー表示**
   - Bluetooth権限および位置情報権限ダイアログの直前に「画面を閉じている間も、ペアのiPhoneが近くにあった日と時間を推定して記録補完に使用します（地図や現在地画面は表示しません）」と双方に明示する。
   - カメラ権限はQR読取時のみ。
   - プライバシーポリシーとApp Privacy申告を実装（CloudKit利用範囲・E2EE保護・14日自動削除・データ保存と削除の違い）と一致させる。
3. **審査での再現性確保**
   - 別々のiCloudアカウントを使うiPhone 2台で、QR設定 → ロック → 再接続 → 履歴表示までを撮影した外撮り動画を用意する。
   - レビュアーが1時間待たずに履歴UIを確認できるサンプル／手順を用意する。
   - ストア説明文は「100%全自動記録」と言い切らず、「近くにあった日と時間を自動で記録・候補として残します」など実測に沿った表現にする。

## 8. 開発環境とプロトタイプ検証計画（次のアクション）

### 現在の開発環境制約と進め方
- **手元のiPhoneは1台**（シミュレータはBluetooth非対応）。
- **ステップ1（手元開発）**：手元の **iPhone 1台 ＋ 開発用Mac（相手役のBLEツール）** で、接続・認証・切断・ログ保存の基本動作を作る。
- **ステップ2（本番環境実験）**：TestFlightで彼女のiPhoneに入れ、**デバッガを外した普段使いのiPhone 2台**で以下の検証を行う。

### 実機2台で合否を決める検証項目（外部レビュー基準）
**最重要テスト**：「前日に対面設定 → 別々に帰宅 → 翌日どちらもアプリを開かずに60〜90分会って別れる → 解散後に初めてログ確認」（会っている最中にアプリを開いて確認するとロック状態の条件が壊れるためNG）。

| # | 検証シナリオ | 確認する指標 |
|---|---|---|
| **1** | **両方画面ロックのまま再会**（片方画面オン条件とも比較） | 未検出率、開始・終了の遅延時間（未検出の回も隠さず記録） |
| **2** | **接続後、無操作で8時間就寝**（途中の別室移動・朝の外出含む） | 朝までの維持率、過大計上・途中欠損の有無、自動記録OFFの夜とのバッテリー消費差 |
| **3** | **一人がスマホを家に置いて外出／隣室・壁越し** | 通信が正常でも起きる誤記録の頻度・距離感の把握 |
| **4** | **異常系**（片側スワイプ終了、再起動、Bluetoothオフ、圏外解除） | 欠測が「終了不明」になるか、再送で二重計上しないか、解除後に旧記録が戻らないか |

### 実験結果による仕様確定の分岐（仮の判断ライン）
* **合格ライン（仮）**：1時間以上の会合で「日付検知95%以上」かつ「時間誤差が1時間以内の回が90%以上」
  - **両方クリア** → 当初構想どおり「開始〜終了の時間レンジ＋カレンダー」でMVP本実装へ。
  - **日付のみクリア（時間が不安定）** → 時間は参考値または見送り、「会った日カレンダー＋一言メモ」中心へ仕様調整。
  - **両方ロック再会の取りこぼしが多発** → 付帯機能を作る前に、「ワンタップチェックイン＋Bluetooth補助」方式へ方向転換。

## 9. 意思決定ログ（Why早見表）

開発中に迷ったとき用のクイックリファレンス。

| 疑問 | 決定した仕様 | 理由（Why） |
|---|---|---|
| なんでBLEと位置情報を併用するの？ | BLE ∪ 正確な位置情報（E2EE CloudKit 突き合わせ） | BLE単独では画面消灯やOS終了で取りこぼしが出るため。地図UIは一切出さず E2EE で時間重なりだけ計算することで「監視感ゼロ」と「取りこぼし根絶」を両立する。 |
| なんで最小単位が1時間？ | 1時間単位（分単位にしない） | BLEの接続タイムラグ・トイレ離脱・夜間スリープの微細なズレを誤差として吸収できるため。 |
| なんで検知後に切断せず繋ぎっぱなし？ | 接続維持＋切断で終了検知 | 新規スキャンは画面消灯で止まりやすいが、確立済み接続は寝ていても維持されやすく、時間レンジを取りやすいため。 |
| なんでLive Activityで夜間スキャンしない？ | 夜間対策には使わない | iOS 26でも完全消灯時は探索制限が戻り、8時間上限や裏起動制限もあるため。 |
| なんで発見だけで記録せず認証するの？ | 接続後にペア専用認証を実施 | Overflow Areaは128bitハッシュのため、他人のiPhoneと約1/128で衝突・誤検知するから。 |
| なんで手動修正が必要なの？ | 自動記録＋手動追加・修正可 | スマホ置き忘れや短時間デートなど、通信が正常でも現実とズレるケースが必ずあるため。 |
| なんで「終了不明」を作るの？ | 終了欠損時は時間加算しない | 電池切れやスワイプ終了のあと、翌朝起動時刻を終了にすると数十時間の過大計上になるため。 |
| なんで「別れたボタン」がないの？ | 「ペア連携解除（機種変・再設定）」に統合 | 縁起が悪い言葉を避けつつ、CloudKit共有解除・機種変・App Store審査要件を1つで満たすため。 |
| なんでメモ帳や予定表は後回し？ | まずBLEプロトタイプ→MVP | 肝心のBluetooth検知精度が実用に耐えるか先に検証しないと、付帯機能を作り込んだ後に手戻りが大きくなるため。 |
| なんでiOS 26以上限定？ | Deployment Target = iOS 26 | 最新BLE再接続・CloudKit 1回限り招待URL・CKSyncEngineを分岐なしで綺麗に使うため。 |
